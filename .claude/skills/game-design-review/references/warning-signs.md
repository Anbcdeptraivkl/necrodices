# Warning signs and the next step

Review prompts, not a fun score. Small samples guide experiments; they do not prove demand.

## Warning signs and immediate checks

| Warning sign | Check before doing more work |
| --- | --- |
| It will become fun once we add another system | Show the existing payoff; identify exactly what is missing |
| One routine solves nearly every strategic situation | Compare actual outcomes, costs and reasons to deviate |
| More difficulty only means more HP or repetition | Test whether players need a different response |
| Every build converges on the same purchases / actions | Compare behaviour and reward priorities, not starting stats |
| Many buttons but little influence over the result | Trace one decision through a visible consequence |
| Upgrades feel weaker or need an explanation to feel good | Compare experienced power, lost capabilities and fantasy |
| Rewards mostly extend the same routine | Try one reward that changes a plan or execution |
| Docs, refactors and trackers grow faster than play evidence | Schedule the smallest real-input test before more expansion |
| A mechanic is justified mainly by a successful reference game | Identify its supporting constraints and test them locally |
| Existing assets / code are the main reason to keep a feature | Ask whether you would choose it in a fresh prototype |
| Timebox passed, status still "built, awaiting playtest" or "ok for now" | Write keep / change / cut now, or name the one missing piece of evidence |

## Decide the next step

| Evidence | Next step |
| --- | --- |
| A compelling moment recurs; players understand it | Expand one supporting dimension and verify the payoff survives |
| The result is unclear | Fix readability / feedback or isolate one assumption; keep scope bounded |
| Players understand the loop and find it dull | Change the central interaction or payoff; defer extra progression / content |
| Bounded experiments repeatedly produce no compelling moment | Shelve the concept; keep useful tools without inheriting its rules |

Choose the time / iteration budget **before** trying to rescue an idea (default: two
experiments, one axis each). Keep enough visual and audio feedback to judge the intended
experience; final art and generalised frameworks wait. Streamlining reduces friction — the
enjoyable moment still needs testing.
